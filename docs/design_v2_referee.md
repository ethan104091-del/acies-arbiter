## 〇、v2 要做什麼

把單機遊戲拆成 **前端／後端／資料庫**，並讓**大型語言模型裁判逐小時真的去判**，
而不是由人逐回合驅動。每桌對局一個獨立裁判。

三方各自輪詢後端：

```
指揮官前端  ──輪詢──▶  後端  ◀──輪詢──  裁判工作者
（送命令、問狀態、收戰報）   （權威狀態＋佇列）   （取件、判、寫回）
```

前端不提供被呼叫的介面。所有迷霧過濾在後端完成，介面以陣營為授權單位——
**後端絕不回傳未過濾的戰場資料讓前端自己遮**。

## 一、宗旨（第一條已重寫）

原本的四條是：規則用自然語言寫、大型語言模型當裁判（讀規則、解算戰鬥、維護迷霧、產戰報）；
零機率確定性；三層戰爭迷霧；裁判透明（裁示逐位元組相同發雙方、自己的錯也公開、判例累積成法）。

**第一條在 Phase 1–3 之後已經名實不符**：維護迷霧早就是程式碼、解算歸引擎、
數值全在 `rulespec` 註冊表。四個動詞裡兩個半已不由大型語言模型執行。
README 目前仍照舊描述，形同「對外承諾了一件引擎不做的事」——與 S4 同型。

改寫為：

> **規則以自然語言為權威住址；執行必須經過閘門；規則未涵蓋處由裁判當場裁定，
> 並累積成判例回頭進註冊表。**

這句是真的，而且描述的東西比原句更少見：一般遊戲的規則爭議是設計者私下改，
這裡是公開判、留紀錄、下一局變成規則。

## 二、裁判是無狀態的

**「一個對局一個裁判、活著跑完 54 小時」不行。**
它上一小時記得什麼、想過什麼，沒人查得到，那就是第四個不確定性來源，
直接違反「不確定性只有三個來源」。

所以：**每小時一份卷宗，裁判讀完就死。** 脈絡從紀錄重建。

### 卷宗內容

- 這小時開始時的**全知**戰場狀態
- 雙方常設命令與應變欄，**原文**
- 規則
- 判例
- 上一小時的事件紀錄

「挑相關的規則／判例」是陷阱——挑選本身就是判斷，而且是隱形的。
**卷宗裡放了什麼必須留痕**，否則裁判漏看某條判例時無從追究。

### 掛載點

引擎早就留好位置：`run_tick` 每小時呼叫一次 `resolve(s, gh)`，
原註解寫的就是「裁判的裁示注入點——移動、砲擊、地面戰、任何前所未見的動作」。
v1 塞在那裡的是手寫 Python，v2 換成裁判。**這不是改架構，是接原本就預留的插座。**

管線順序保證裁判每次看到的是上一小時全部結算完的狀態（疲勞、工事、能見、
返火、組織度恢復、狀態機都跑完）。

## 三、輸出分三層

| 輸出 | 可見層 | 去處 |
|---|---|---|
| 動作 | 全知 | 引擎執行 |
| 裁示 | 公開 | 雙方逐位元組相同 |
| 徵候 | 單方 | 各自視角 |

三者**結構上分開**，不是像 v1 那樣混在 `ev` 事件清單裡靠 target 欄位分流——
那是紀律，不是結構。

## 四、兩級動作集

宗旨要裁判能做「前所未見的動作」，但動作集不封閉就沒有閘門。
解法是**讓旁路變成有代價的正門**：

- **一級**：引擎實作過的動作。呼叫即執行，決定性，可重放。
- **二級**：引擎沒有的。裁判**必須先寫裁示**（依據、理由、對哪一方有利）才能改變狀態，
  且該動作在紀錄裡永遠帶著那份裁示。

新動作不被禁止，只是要公開判決。而它自動成為判例來源：
**這一局的二級動作，下一局進註冊表變一級。**

v1 四局的執行錯誤（逼退當行軍、沿用舊目的地、白給 13,988 工時、`push<0` 四局從未執行）
全發生在無聲的旁路上。有了兩級制，同樣的事還能做，但做了就留痕。

**裁判在任何情況下不得直接寫狀態，只能呼叫動作。** 判斷自由，執行沒有旁路。

## 五、裁判守則（十條）

先認清一件事：**「必須寫裁示」本身不構成限制**——大型語言模型能替任何決定寫出通順的理由。
所以守則要壓在可機械檢查的地方。

### 事前（引擎可強制）

1. **時點**　二級動作必須在該小時結算**之前**登記，落定後不得追加。
   判的時候還不知道誰會被打、打多重，就不可能挑對誰有利的數字。
   （判例裡已有一次「裁判在看到結果之後才做出翻轉勝負的裁示」。）
2. **形式**　裁示必須寫成「條件 → 效果」，且**條件不得指名陣營**。
   對稱性因此是形式問題，不是良心問題。
3. **不得繞道**　一級動作能表達的不准走二級。裁判須宣告「為何一級不夠」，該句事後可驗。
4. **不得引入機率**　裁示裡不得有擲骰、約略、大概。效果必須由狀態算得出來。

### 上限

5. **量級門檻**　單次二級動作對任一方戰力或分數的影響超過設定比例 → **強制轉待人工裁定**，
   裁判無權自行落定。
   *這條是整套守則裡最重要的：把「小事裁判自己判、大事要人」從紀律變成結構。門檻值待試。*

### 事後（可統計）

6. **必須標明對哪一方有利**　價值不在自省，在於能累計——每一方受益的裁示數擺出來，
   傾斜就看得見，不用等人指控。
7. **不得追溯**　裁示自公告起生效，不回頭改已落定的小時。要改走勘誤，另立紀錄、發雙方。

### 出口

8. **不確定就問，不准硬判**　裁判判不了的走待裁定。這不是失職，硬判才是。
   *唯一靠自律的只有這條，所以要靠別的補：**待裁定用得太少本身就是訊號**，進每局檢討。*

### 依據

9. **史實錨定（管數值合理性）**
   - **形式**：錨點要可反駁——寫明時期、裝備、情境、數量級
     （例：「1944 西線，105mm 對開闊地無工事步兵，每 100–300 發 1 名傷亡」），
     不是「二戰時通常如此」。
   - **綁定**：錨點一經採用即綁定，同類情況必須沿用；要推翻得明說推翻，
     不能默默換一個。**防止裁判每次挑對當下方便的史實。**
   - **缺錨點時誠實標記**：寫「無錨點，以最小解讀推定」，不准杜撰。
     這種標記累積起來就是規則書該補的清單。
   - **與第 2 條的關係**：錨點定的是**量級**，不是陣營加成。史實上兩軍裝備教範確有差異，
     但純戰場是對稱劇本；真有差異要寫成雙方都適用的條件式（「配備 XX 者如何」），
     不能寫成「紅軍如何」。否則第 2 條會被第 9 條吃掉。

10. **時空可行性（管准不准發生）**
    裁判最危險的權力不是給錯數字，是**憑空生出東西**——二級動作能改變狀態，
    理論上就能讓補給隊抬一台鋼彈進來。判準不是「合不合理」，太軟。改成**三問**：

    1. 哪個單位做這件事？（要指到編制表上的具體單位）
    2. 用什麼器材？（要指到該單位實際擁有的裝備）
    3. 要多久、耗什麼？（時間與消耗必須算得出來）

    | 情況 | 處置 |
    |---|---|
    | 編制內有 | 准 |
    | 當時存在、該方可能取得，但不在編制內 | 走裁定，付時間與後勤代價 |
    | 當時不存在 | 駁回 |

    - **駁回必須回覆指揮官，不得靜默忽略**——否則他照著沒生效的命令規劃下一步，
      那是「規則書承諾引擎不做的事」搬到命令層。
    - **同一把尺套在裁判自己身上**：二級動作登記時要過同樣三問；
      人員／裝備／彈藥的增減必須有來源（現有編制、補給流、或繳獲），
      由引擎硬性驗證守恆，裁判無權豁免。

## 六、指令多樣性（已評估）

拿 Run 7 T5 藍軍定稿對照過。實際命令遠超出動作集的五個動詞，同一份裡就有：
條件性目標切換、有順序的任務鏈、用述詞挑執行者、集合層級的分配約束、
帶時效的自我約束、拆分＋沿路徑作戰＋歸建。

**但這不構成問題，因為命令清單不是指令格式**——它是「這小時實際允許發生什麼」的
授權清單，是輸出不是輸入。指揮官照樣寫散文，裁判逐小時把常設命令、應變條件、
述詞展開成當小時的具體動作。**那個展開才是真正的工作量，多樣性也在那裡。**

兩條紅線：

- **要指揮官直接寫結構化命令 → 多樣性崩到五個動詞。這條路不能走。**
- **展開不出來時不准靜默近似**（例：「沿補給走廊掃蕩、肅清後歸建」）。
  超出可執行動作集就報錯進待裁定——這是 S4 換到命令層重演。

反過來，閘門化其實**擴大**一種多樣性：應變欄零延遲、觸發即生效，
六條 × 兩方 × 每小時要逐條檢查，人做不到（四局的錯有幾件正是漏檢），
自動展開能穩定做到，指揮官才敢寫更複雜的應變。

**「給裁判的問題」通道必須保留。** Run 7 T5 問的「8% 上限的計量單位」
直接決定他整個火力編組怎麼編。沒有問答通道，這種命令根本不能下。

## 七、腳本與重放

裁判接上去之後**不需要 `t*.py` 腳本**，但要有替代物。

腳本現在扛兩個角色：執行載體（它本身就是 `resolve`）、稽核紀錄（重放靠跑它）。
第一個角色消失，第二個轉移到**逐小時的決定紀錄**。

**這是升級不是降級**：腳本是程式碼，能做任何事包括繞過引擎；
決定紀錄是資料，只能是動作集裡列舉過的東西。
**能被重放的，從此在構造上就沒有旁路。**

### 重放的定義

決定一旦落定，就成為輸入的一部分。**重放 ＝ 引擎 ＋ 已落定的決定。**

這不牴觸「不擲骰」：骰子是每次重跑都不同，落定的判斷是永久的——
跟史實一樣，發生過就不能重來。

### 三個但書

1. **舊的 52 支腳本不能刪。** run4–7 的重放靠它們，這也是 `arbiter` 對外的
   **113 個名字一個都不能動**的原因（58 個檔在用）。新做法只從 Run 8 起算。
2. **要寫一支重放器**（讀決定紀錄餵引擎）。目前不存在。
3. **腳本裡的推導不能跟著消失**——那些「為什麼這樣算」的註解該進裁示文本，
   它本來就該是裁示，只是以前寫在程式碼註解裡。
4. `tests/test_audit_manifest.py` 那套故障注入測試保留，它重現的是歷史錯誤，與對局紀錄無關。

## 八、後端要點（尚未細設計）

- **取件要鎖定、要有租約**：同一桌不能被兩個裁判同時解算；裁判掛掉要能逾時重派。
- **回合編號當冪等鍵，只能落定一次**：重派時若上次已寫回結果，必須拒絕第二次寫入，
  否則戰史不可信。前端送命令同理，丟包重送靠冪等鍵去重。
- **待裁定是常設路徑**，不是暫時補丁：要有自己的介面、狀態、發布流程。
- **資料庫存事件序列**，當前狀態是推導出來的，不是唯一真相：
  桌／回合（狀態、提交窗口、租約）／命令（陣營、原文、冪等鍵）／
  決定紀錄（結構化動作＋逐項出處）／快照（回合起始全量）／裁示與戰報（雙方各一份＋共用段落雜湊）。
  共用段落存雜湊，是為了讓「雙方收到的東西逐位元組相同」變成可查的事實，而不是靠紀律。
- **成本要先算**：54 小時 = 54 次裁判呼叫／桌，每次要餵全知狀態、規則、
  雙方常設命令與應變。成本與延遲是逐回合做法的六倍，一個回合的解算落在分鐘到十幾分鐘級，
  直接決定租約時長與輪詢間隔。
